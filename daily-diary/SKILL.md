# Daily Diary

帮助用户留下像自己写的日常记录。不是一份关于用户的报告，也不是聊天日志拼接。
本 skill 使用用户已有的资料范围、权限与发布授权；安装本身不授予读取或发送权限。

先读 [原始意图](references/original-intent.md)。
写作或修订时读 [写作指南](references/writing-guide.md)。
汇总、补采或补写时读 [资料契约](references/source-contract.md)。
发布、定时任务及运行故障时读 [部署与验收](references/deployment.md)。

## 不变的要求

- 第一人称，优先保留用户原话和真实关注点。文风依据是用户旧日记、当天表达和确认过的成稿。
- 保持独立的 `## 工作记录` 与 `## 日记`。个人日记不能是工作摘要。
- 有足够可靠时间戳时保留时间线；不要填满无证据的小时。
- 不编造起睡、行程、地点、会面、感受、动机或因果。未知保持未知。
- 时间线、工作记录、日记和图注统一用本人视角；核对在后台完成，不把成稿写成助手的资料审计。
- 修订默认保留已有事件、段落、图片和来源表；润色不等于删减授权。
- 原始会话和微信数据库只读；只写获准的导入、草稿和日记目录。
- 默认仅向日记主人交付。其他人的聊天只取与本人当天经历必要相关的部分。
- 不因为资料失败而绕过会话隔离、机器人控制、ROS、CAN、服务管理、网络配置或提权限制。

## 工作模式

### 晚间回顾

当前部署默认 22:00。沿用主人的微信直聊上下文，自然询问当天值得留下的片段。
一次追问少量有价值的细节，不做问卷，不替用户规定心情，不立即生成正式日记。
结束时简短复述记录重点，留出纠正机会。

### 随手记录

先正常回应，再保存原话、语境和明确日期。含糊处仅追问影响记录的关键问题。
不把一句话扩写成未确认的故事。

### 次日整理

当前部署默认：09:45 宿主同步资料，10:00 同一微信直聊给出写作提要。
自动写作任务读目标日的 manifest 和规范化快照，不重复采集或直接 SSH。
人工补采必须在获准范围由宿主采集工具执行，不启动、结束或重启微信。
若部署提供受限 outbox，请在主人明确要求补采时提交日期与来源请求，
由宿主执行并返回状态，不把“无直接 SSH 权限”误报为“无法补采”。

核对每个来源状态及覆盖时间，吸收同一直聊中的昨晚回复和后续补充；
跨日期和其他会话中的材料仅作明确相关的背景，不能混作当天经历。
先给简短提要：生活片段与感受、工作成果与经验、资料缺口、少量待确认问题。
用户纠正和补充后生成正式版。用户要求直接写时可以先出草稿，未知不填造。

### 兜底与历史补写

当前部署默认次日 13:00 检查昨日是否完成归档。未回复不应造成永久漏日：
根据已有证据写短而诚实的版本，缺失细节省略，重要缺口最多文末一小段，之后可修订同一日期。
这与“默认先讨论”并不冲突：先发提要，兜底时保留未确认状态，不伪造同意。

补写先检查指定范围每个日期的 Markdown、PDF、提交、远端和发送状态。
只补缺失或待修订日期；不重复发送已成功的附件。
不能把成功封稿一日说成整段历史已完整恢复。

## 输出与交付

使用部署明确的 `DIARY_REPO`，按 `YYYY/MM/YYYY-MM-DD.md` 和 `.pdf` 保存。
用 [模板](assets/diary-template.md) 作骨架，标题和段落服从当天内容。
真实生活日优先实际起床至实际睡觉，凌晨睡前延续的活动默认归前一天，用户纠正优先；
缺少证据时以部署时区 05:00 至次日 05:00 作后备归档窗，不声称这是实际作息。

用 `scripts/generate_diary_pdf.py` 生成 PDF。检查字体嵌入、文本完整性及非空渲染，
并实际查看渲染页是否乱码、裁切或排版失常。失败则停止发送，不静默改发长文字。

重排、样张及重发前，同时检查同日草稿、归档和后续本人补充；已归档不代表内容最新，
文件修改时间也不能代替内容比较。先合并有效补充，保留确认状态，再改排版。
仅改排版时必须传 `--content-reference 最新完整稿.md`；有分歧的多份版本可重复传入。
该检查逐段保留正文、表格单元格与配图，缺失则停止生成。它防止版本回退，
不证明原始资料全部覆盖，也不代替本人授权改写时的语义核对。

授权发布时统一执行 `scripts/publish-diary.sh`；
无 `DIARY_PUBLISH=1` 只生成验证，不提交不推送。
只有脚本返回 `status=published` 才能报告已推送，保留提交号。
随后用已配置的消息工具发送短说明和 PDF 文档附件，核对附件投递结果与消息 ID。
只有用户明确要求文字版才发送全文。

完成时区分：资料读取、成稿、PDF 验证、Git 推送、微信附件投递。
每个阶段独立验收；失败保留已有成果并明确报告阶段，不冒充全流程成功。

维护本 skill 时，将通用规则与部署个性化配置分开。修改后运行测试、检查私密信息，
在已有仓库发布授权范围内提交推送并核对远端提交；未推送就明确报告，不把本地生效当作仓库已同步。
